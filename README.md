# RateLama

RateLama (https://www.ratelama.de) ist eine deutschsprachige Quiz-Anwendung mit React, TypeScript, Vite und AWS Amplify Gen 2. Quizmaster verwalten Quizze und steuern Live-Sitzungen oder veröffentlichen Quizrunden zum Mitmachen; Gäste spielen ohne Konto auf ihrem Smartphone. Eine optionale Live-Präsentationsansicht ist schreibgeschützt.

Eine ausführliche Übersicht über [Funktionen, Design und aktuell verwendete Technik](docs/funktionen-design-technik.md) beschreibt beide Spielarten und den lokalen Entwurfsmodus.

Der frühere Projektname „Ratelama“ bleibt aus Kompatibilitätsgründen in technischen Bezeichnern erhalten (Env-Variablen `QUIZRUSH_*`, Lambda- und Metriknamen, Browser-Speicherschlüssel `quizrush.*`, Paketname).

**Status:** Der Live-Ablauf und ausgewählte Autorisierungs- und Lastfälle wurden in einer isolierten AWS-Sandbox geprüft. Vor produktivem Einsatz müssen Deployment, Alarme, Sicherheit und Lastgrenzen in der jeweiligen Zielumgebung erneut überprüft werden.

## Voraussetzungen und Entwicklung

Benötigt werden Node.js `^22.12.0`, `^24.0.0` oder `>=26.0.0`, npm, AWS-Zugang mit passenden Berechtigungen und ein für CDK gebootstrapptes AWS-Konto. Standardregion ist `eu-central-1`. Ressourcen wie WAF, AppSync, DynamoDB, Lambda und Step Functions verursachen Kosten.

```sh
npm ci
npm run typecheck
npm run lint
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

`npm run lint` nutzt [oxlint](https://oxc.rs) (`.oxlintrc.json`, inkl. `react-hooks`-Regeln); Fehler brechen ab, Warnungen werden gemeldet. ESLint mit `typescript-eslint` unterstützt TypeScript 7 noch nicht. Die GitHub-Action `.github/workflows/ci.yml` führt Typecheck, Lint, Tests, Legal-Check und `npm audit --omit=dev` für Pull Requests aus; Dependabot (`.github/dependabot.yml`) hält Abhängigkeiten aktuell.

Ohne `amplify_outputs.json` bietet die Anwendung ausschließlich einen ausdrücklich gekennzeichneten lokalen Entwurfsmodus. Dieser ist **kein geschützter Admin-Bereich**. Die Entwurfsspeicherung ist zunächst ausgeschaltet; erst nach Aktivierung werden vorhandene Entwürfe gelesen, und neue Entwürfe werden nur nach ausdrücklichem Speichern dauerhaft in diesem Browser abgelegt. Das Ausschalten löscht keine vorhandenen Daten.

## Oberfläche und Bedienung

Cremetöne, kräftiges Grün und das winkende RateLama prägen die Startseite. In der Quizübersicht zeigen pastellfarbene Karten die tatsächliche Fragenzahl; ihre Farben haben keine spielerische Bedeutung. Grün kennzeichnet die Hauptaktionen, und abgerundete Balken begleiten die vorhandenen Fortschrittsangaben in Editor und Spiel. Die gemeinsamen Farben, Schrift-, Karten-, Button- und Fokusregeln stehen in `src/ui/base.css`; Start, Live-Spiel, Quiz zum Mitmachen und Quizmaster-Bereich haben eigene Stylesheets unter `src/ui/` (`home/`, `live/`, `async/`, `admin/`, `game/`). Die gesamte Oberfläche liegt unter `src/ui/`, die Routen stehen in `src/App.tsx` und `src/ui/routes.ts`. Navigation, Formulare und Quizansichten passen sich vom schmalen Smartphone bis zum Desktop an; Schriftarten und Grafiken werden ohne externe Dienste geladen.

Bestätigungen beim Löschen, beim Beenden einer Runde und beim Verwerfen lokaler Änderungen erscheinen als einheitliche Dialoge im App-Design. Der Tastaturfokus startet auf „Abbrechen“, bleibt im Dialog und kehrt beim Schließen zum Auslöser zurück (wenn dieser nicht mehr verfügbar ist, zum Hauptinhalt). Escape bricht ab; ein Klick auf den Hintergrund bestätigt nichts. Beim Schließen oder Neuladen eines Tabs mit ungespeicherten lokalen Änderungen bleibt der technisch notwendige Browserdialog erhalten.

Auch der vorläufige Zwischenstand unter `/admin/async/:publicationId` zeigt die ersten drei Teilnehmenden auf dem gemeinsamen 2–1–3-Podium mit Punkten und Teilnahmestatus. Gleiche Ränge behalten dieselbe Podesthöhe. Alle weiteren geladenen Platzierungen stehen direkt darunter; zusätzliche Teilnehmende können nachgeladen werden. Im Endstand bleiben die weiteren Plätze ab dem sechsten Eintrag aufklappbar.

Der Editor arbeitet in zwei Schritten: „Grundlagen“ (Titel, Kategorie, Beschreibung) und „Fragen“. Die Kategorie (Allgemeinwissen, Geografie, Wissenschaft, Tiere & Natur, Team & Freunde) wird im Backend am Quiz gespeichert; ältere Quizze ohne Kategorie erscheinen als Allgemeinwissen. Auswahlkreis, Rahmen, Häkchen und Lösungstext zeigen die richtige Antwort. Die Fragenleiste springt direkt zur jeweiligen Frage und kennzeichnet fertige Fragen. `/admin/quizzes/:quizId` zeigt die Quizdetails, bearbeitet wird unter `/admin/quizzes/:quizId/bearbeiten`. Im Live-Spiel wird eine Antwort direkt beim Auswählen gesendet und kann bis zum Ablauf der Fragezeit geändert werden. Das gilt für alle Live-Quizfragen; vorzeitiges Schließen oder Abbruch beendet die Änderungsmöglichkeit ebenfalls. Nur die zuletzt rechtzeitig vom Server angenommene Auswahl zählt. „Wird gesendet …“ und „Antwort ist drin“ sind getrennte Zustände; beim Wechsel bleibt die bisherige Antwort gespeichert, bis der Server die neue Auswahl bestätigt. Während des Sendens oder der Wiederherstellung sind weitere Eingaben kurz gesperrt. Die eigene Antwort bleibt während der Auswertung und Auflösung markiert und wird nach Neuladen oder Wiederverbindung vom Server wiederhergestellt. Auch nach einer verlorenen Sendebestätigung wird zuerst die gespeicherte Antwort geprüft; ein abgelehnter Wechsel lässt die vorherige Antwort gültig und zeigt einen Fehler. Bei angezeigtem Fristende sperrt die Oberfläche die Eingabe, ohne selbst in die nächste Spielphase zu wechseln.

Antwortwechsel benötigen das passende Backend aus `src/server/submitAnswer.ts` und die aktualisierte Spieleroberfläche; ein reines Frontend-Update reicht nicht. Die bestehende GraphQL-Schnittstelle und gespeicherte Antwortdatensätze bleiben kompatibel, eine Datenmigration ist nicht erforderlich.

Frage, Auflösung, Zwischenstand und Endstand sind getrennte Ansichten derselben serverseitigen Spielphasen. Live- und Mitmachfragen zeigen die aktuelle Frage als Bruch und Balken; der beantwortete Anteil bleibt davon getrennt. Die gemeinsamen Antwortkarten (`src/ui/AnswerCards.tsx`) und Belohnungen (`src/ui/game/`) nutzen Live-Spiel und Quiz zum Mitmachen gleichermaßen; Rückmeldung und Punkteanimation sind vom Spielablauf entkoppelt. Spiel- und Live-Layouts stehen in `src/ui/game/game.css` und `src/ui/live/live.css`. Mobil sind Frage und vollständige Antworten, persönliche Rückmeldung, tatsächlicher Punktgewinn und Gesamtpunkte ohne Beamer verfügbar. Ein bereits bekannter Rang wird während der nächsten Frage ausdrücklich als letzter Rang bezeichnet; vor der ersten Wertung wird kein Rang erfunden. Rangänderungen werden erst ab einem echten Vergleich nach der zweiten Frage angezeigt.

Die Präsentation enthält keine Adminnavigation. Sie zeigt Stimmenbalken bezogen auf **alle abgegebenen Antworten**, nicht auf die Teilnehmerzahl; Nichtantworten werden separat genannt. Zwischen- und Endstand zeigen ein Podest in der Anordnung 2–1–3 mit unveränderten Serverrängen (gleiche Ränge haben gleiche Podesthöhe) und höchstens fünf weiteren Zeilen. Mobil stehen die eigene Position und benachbarte Plätze im Mittelpunkt. Lobby-Vorschauen sind auf zwölf Avatare, mobil auf sechs begrenzt; die Gesamtzahl bleibt sichtbar. Beim Quizmaster gibt es nur den zum Serverzustand passenden nächsten regulären Schritt. Countdown, Fristende und Auswertung bleiben automatisch; vorzeitiges Schließen und bestätigter Abbruch sind nachrangige Aktionen.

Die bestehende Abfrage `getMyResult` liefert zusätzlich `totalPoints` aus dem eigenen serverseitigen Teilnehmerdatensatz, ausschließlich nach abgeschlossener Auswertung und mit erneuter Snapshot-Prüfung. Für diesen Frontendstand ist das passende Backend-Schema aus `amplify/data/resource.ts` erforderlich; ein reines Frontend-Update gegen das alte Schema reicht nicht.

Bestätigte Punktgewinne bekommen ein Punkte-Popup, animierte Zähler und kurzes Konfetti. Rangaufstiege werden hervorgehoben; Zwischenstände erhalten animierte Ranglisten und ein gestaffeltes Podium, das Finale eine größere, automatisch endende Feier. Lobby-Avatare, Countdown, Antwortbestätigung und Stimmenbalken haben zusätzliche kurze Effekte. Neue Abzeichen und Serien werden persönlich angezeigt. Identische Ergebnisse und ein erneutes Laden erzeugen keinen neuen Punktgewinn. Bei `prefers-reduced-motion: reduce` entfallen Partikel, Zählerfahrt und Positionsbewegungen; echte Zahlen, Häkchen, Ergebnismeldung und Erfolge bleiben sichtbar. Tastaturfokus, ein Sprunglink zum Inhalt, beschriftete Formularfehler und Textmarkierungen ergänzen die Farben. Die Browserprüfungen ersetzen keine vollständige Prüfung mit assistiven Technologien.

Lama-Stimmungen (neugierig, jubelnd, überrascht, stolz), Abzeichen und Rangsymbole sind als SVG-Komponenten im Code gezeichnet (`src/ui/LlamaCharacter.tsx`, `src/ui/Illustrations.tsx`, `src/ui/game/BadgeIcon.tsx`) und benötigen keine Bilddateien. Bekannte Abzeichen-IDs sind fest ihren Symbolen zugeordnet; unbekannte IDs behalten ihren Text und erhalten ein neutrales Symbol. Lokale Bilddateien gibt es nur noch für die Tieravatare unter `public/assets/avatars/`. Das früher gelieferte Grafikpaket liegt unverändert unter `spec/ratelama-gamification-assets/`; die App lädt es nicht. Eine Finale-Feier startet nur beim tatsächlichen Übergang und nicht beim erneuten Öffnen eines bereits abgeschlossenen Ergebnisses.

Unter „Live-Spielregeln“ auf der Quizkarte und im Async-Veröffentlichungsformular können Quizmaster Streak-Bonuspunkte für die neue Runde aktivieren (Standard: aus). Die Regel `STREAK_V1` bringt bei drei richtigen Antworten in Folge +100 Punkte, bei vier +150 und ab fünf jeweils +200 zusätzlich zur bisherigen Wertung. Falsche oder fehlende Antworten unterbrechen die Serie. Serien und Abzeichen („Erstes Aha!“, „Dreier-Serie“, „Unaufhaltsam“, „Perfekte Runde“) gibt es auch ohne Bonuspunkte; Abzeichen selbst geben keine Punkte. Die perfekte Runde benötigt einen vollständigen, ausschließlich richtigen Abschluss. Regeln und Gewinne werden serverseitig gespeichert; Retries schreiben Punkte und Fortschritt nicht doppelt. Historische Runden bleiben unverändert.

Quiz per Link hat eine unabhängige Veröffentlichungsoption „Sofortige Auflösung“, im Formular für neue Runden standardmäßig an. Sie zeigt ausschließlich bereits bestätigte eigene Antworten samt Lösung, Erklärung, Punktegewinn, Gesamtstand und Serie; zukünftige Fragen bleiben verborgen. Erst „Weiter“ öffnet die nächste Frage und startet deren Tempo-Bonus. Nach der letzten Auflösung folgt der persönliche Abschluss. Bei ausgeschalteter Option oder historischen Veröffentlichungen bleiben Lösungen, Punkte, Serien und Abzeichen bis zum Rundenende geheim. Früh sichtbare Lösungen können während der Runde weitergegeben werden; darauf weist das Formular hin. Backend, GraphQL-Schema und Frontend müssen gemeinsam aktualisiert werden; ein Frontend-Update allein reicht nicht. Ein Cloud-Deployment wird durch diese Änderungen nicht ausgeführt.

`npx playwright test e2e/design.spec.ts` prüft die Spielansichten bei 320, 390, 430 und 1440 px sowie die Präsentation bei 1920 px. Die Tests verwenden kontrollierte API-Antworten und prüfen auch lange Texte, zwei/vier/sechs Antworten, Nullstände, Gleichstände, Reconnect, Ergebnisfehler und verlorene Bestätigungen. Abschluss-Screenshots landen unter `test-results/design-*/*.png`. Diese Browserprüfung und `src/server/gameState.test.ts` belegen keine echte AWS-Mehrgeräterunde; dafür ist weiterhin der unten beschriebene Live-Test mit einer ausdrücklich bereitgestellten isolierten Sandbox nötig.

Datenschutz ist dort eingebettet, wo Entscheidungen fallen, statt als Banner über jeder Seite: Vertrauens-Chips direkt unter den Startseiten-Aktionen („Ohne Konto · Ohne Klarnamen · Ohne E-Mail“) führen zu einem eigenen Abschnitt „Datenschutz ohne Kleingedrucktes“ auf der Startseite. Die Beitrittskarte zeigt einen kompakten Hinweis mit aufklappbaren Details, die Fußzeile bietet auf jeder Seite – auch während des Spiels – eine aufklappbare Kurzinformation, und die Kontoanlage weist auf die Speicherung der E-Mail-Adresse hin. Lokale Browserentwürfe und Live-Spiele werden dabei unterschieden; die optionale Entwurfsspeicherung ist standardmäßig ausgeschaltet und wird nicht automatisch als rechtlich ausreichende TDDDG-Einwilligung bewertet. Gäste müssen keinen Namen und keine E-Mail-Adresse eingeben; das bedeutet ausdrücklich **nicht**, dass keine Daten gespeichert werden: technische Kennungen, automatisch vergebene Spielnamen, Avatare, Antworten, Antwortzeiten und Punkte werden für den Spielbetrieb verarbeitet und gespeichert. Für Quizmaster-Konten werden außerdem E-Mail-Adressen gespeichert. Die Hinweise sind eine Kurzinformation, keine vollständige betreiberspezifische Datenschutzerklärung.

## AWS-Sandbox und Administration

AWS-Profil und Region auswählen; Sandbox-Namen müssen weniger als 15 Zeichen lang sein:

```sh
AWS_PROFILE=<profil> AWS_REGION=eu-central-1 npx ampx sandbox --identifier <kurzer-name>
```

Die Sandbox erzeugt `amplify_outputs.json`. Für den Vite-Entwicklungsserver die Datei unter `public/amplify_outputs.json` bereitstellen. Sie enthält öffentliche Ressourcenkennungen, aber keine Admin-Passwörter; die Datei wird nicht eingecheckt. Nach Änderungen an den Ressourcen die aktualisierte Ausgabe erneut bereitstellen.

```sh
mkdir -p public
cp amplify_outputs.json public/amplify_outputs.json
npm run dev
```

### Konto über die App anlegen und freigeben

Unter `/admin` **Konto anlegen** wählen, E-Mail-Adresse und Passwort eingeben und die E-Mail-Adresse mit dem zugesandten sechsstelligen Code bestätigen. Bei unterbrochener Bestätigung auf der Anmeldeseite **E-Mail-Bestätigung fortsetzen** verwenden; dort lässt sich auch ein neuer Code anfordern.

Anschließend anmelden. Neue Konten sehen zunächst **Freigabe ausstehend** und können keine Quizze oder Sitzungen verwalten. Die bestätigte E-Mail-Adresse allein verleiht keine Rechte.

Die Administration öffnet in der AWS-Konsole **Cognito → Benutzerpools → den passenden Pool → Benutzer**, wählt das neue Konto und fügt es der Gruppe **`Quizmasters`** hinzu. Der passende Pool steht in `amplify_outputs.json` unter `auth.user_pool_id`. Es muss eine **Gruppenzugehörigkeit im User Pool** zugewiesen werden, keine IAM-Rolle von Hand.

Danach klickt der Nutzer in der App auf **Zugriff erneut prüfen**. Dabei werden die Anmeldungstokens erneuert und die Gruppe erneut geprüft. Bei Problemen ab- und wieder anmelden. Konten werden niemals automatisch der Gruppe zugeordnet, auch nicht das erste Konto.

Die Selbstregistrierung muss durch Deployment des aktuellen Backends freigeschaltet sein; ein reines Frontend-Update genügt nicht. Anschließend die aktuelle `amplify_outputs.json` bereitstellen. Öffentliche Cognito-Registrierung sowie Bestätigungs- und erneute Code-E-Mails unterliegen Cognito-/SES-Versandlimits, Quoten und gegebenenfalls Kosten. Für produktiven Versand Absender, Zustellbarkeit und AWS-Quoten prüfen. Eine eigene WAF begrenzt zusätzlich zum AppSync-Schutz die Anfragen am Cognito User Pool; ihre Grenzen müssen zum öffentlichen Betrieb passen.

### Alternative: administrativ angelegtes Konto

Mit ausreichenden Cognito-Berechtigungen lässt sich weiterhin ein Konto anlegen und der Gruppe zuordnen:

```sh
aws cognito-idp admin-create-user --region eu-central-1 --user-pool-id <user-pool-id> \
  --username <email> --user-attributes Name=email,Value=<email> Name=email_verified,Value=true
aws cognito-idp admin-add-user-to-group --region eu-central-1 --user-pool-id <user-pool-id> \
  --username <email> --group-name Quizmasters
```

Beim ersten Login eines so angelegten Kontos muss das temporäre Passwort geändert werden. Die Anmeldung erfolgt ebenfalls über `/admin`. Dort kann auch das enthaltene Beispielquiz mit zehn Fragen angelegt werden. Die Gruppe allein reicht nicht zum Zugriff auf fremde Daten: Serveroperationen prüfen zusätzlich den jeweiligen Eigentümer.

### Quiz mit KI erstellen

Unter `/admin/quizzes/generate` („Quiz mit KI erstellen“ in der Übersicht) beschreibt ein Quizmaster ein Wunschquiz: Titel, Thema, Anzahl Fragen (1–50), Antwortmöglichkeiten pro Frage (2–8), Schwierigkeit, Tonalität, Zielgruppe, Sprache, Antwortzeit, ob Erklärungen erzeugt werden sollen, sowie optionale Hinweise (Schwerpunkte, Ausschlüsse oder eigener Quelltext). Weil AppSync Anfragen nach 30 Sekunden abbricht, legt `startQuizGeneration` einen Job (`GENERATION#<jobId>`, TTL 1 Tag) an und startet asynchron die Lambda `quizrush-quiz-generator`; die Oberfläche fragt den Status über `getQuizGeneration` ab. Die Lambda ruft die OpenAI Chat Completions API mit Structured Outputs auf, verwirft unbrauchbare Fragen, mischt die Antworten und prüft das Ergebnis gegen das Quiz-Schema. Der Vorschlag öffnet sich im Editor und wird erst beim Speichern als Quiz angelegt. Je Quizmaster sind 3 Generierungen pro Minute erlaubt.

Der OpenAI-API-Schlüssel wird als Amplify-Secret `open_ai_key` erwartet (Amplify-Konsole → Hosting → Secrets bzw. lokal `npx ampx sandbox secret set open_ai_key`). Das Modell ist standardmäßig `gpt-4.1-mini` und lässt sich beim Backend-Deployment über `QUIZRUSH_OPENAI_MODEL` ändern; es muss Structured Outputs unterstützen. Die Eingaben im Formular werden an OpenAI übermittelt.

Beim Deployment ausgewertete Umgebungsvariablen:

| Variable | Standard | Bedeutung |
| --- | --- | --- |
| `AWS_REGION` | `eu-central-1` | AWS-Region |
| `QUIZRUSH_MAX_PARTICIPANTS` | `100` | Atomar durchgesetzte Grenze für Live-Sitzungen; gültig 1–1000. Async-Quizrunden haben unabhängig davon 250 Plätze |
| `QUIZRUSH_RETENTION_DAYS` | `7` | Aufbewahrung neuer Sitzungen; gültig 1–365 Tage |
| `QUIZRUSH_ASYNC_RETENTION_DAYS` | `30` | Aufbewahrung der Ergebnisse von Quizrunden zum Mitmachen nach dem Rundenende; gültig 1–365 Tage |
| `QUIZRUSH_IP_RATE_LIMIT` | `2000` | WAF-Anfragen an AppSync pro Quell-IP und 5 Minuten; für große Runden hinter einer gemeinsamen IP (Schule, Firma) erhöhen |
| `QUIZRUSH_AUTH_RATE_LIMIT` | `300` | WAF-Anfragen an den Cognito User Pool pro Quell-IP und 5 Minuten (Anmeldung, Registrierung, Passwort-Reset) |
| `VITE_PUBLIC_BASE_URL` | aktuelle Herkunft | Öffentliche Basisadresse des Frontends (z. B. `https://ratelama.de`) für kurze Teilnahmelinks, QR-Codes und die Einladung; zur Build-Zeit in Amplify Hosting setzen. Ohne Wert nutzt die Oberfläche die tatsächliche Herkunft, damit lokale und Preview-Instanzen keine Produktionslinks erzeugen |
| `QUIZRUSH_OPENAI_MODEL` | `gpt-4.1-mini` | OpenAI-Modell für die KI-Quizgenerierung (muss Structured Outputs unterstützen) |
| `QUIZRUSH_PRODUCTION_BRANCH` | `main` | Amplify-Branch, auf dem `legal:check --strict` den Build abbricht (in Amplify Hosting setzen) |

Die Werte müssen bei jedem Backend-Deployment gesetzt werden, wenn sie vom Standard abweichen. Die WAF-Grenzen sind zusätzliche grobe IP-Schranken; getrennt davon begrenzt das Backend je technischer Identität und Minute: Beitritt 20, Antwort 30, Teilnahme löschen 10, Lesezugriffe (Spielstand, Ergebnis, Rangliste, Präsentation, Async-Infos) 300, Code-Auflösungen auf der Beitrittsseite und über `/q/<Quiz-Code>` 30 (bremst systematisches Durchprobieren von Codes), KI-Quizgenerierungen je Quizmaster 3. Geteilte IP-Adressen können gemeinsam betroffen sein. Der Cognito-*Identity*-Pool (`GetId`) kann technisch nicht mit WAF verknüpft werden; neue Gastidentitäten sind daher beliebig erzeugbar, und die Identitätslimits allein sind umgehbar. Die IP-Grenze am AppSync-Endpunkt bleibt die maßgebliche Schranke.

**Bekannte Restrisiken:** Mit vielen Identitäten kann jemand die Teilnehmergrenze einer Lobby oder eines veröffentlichten Quizzes ausschöpfen und mehrfach teilnehmen; die WAF-IP-Grenze erschwert das nur. Präsentations- und Async-Links werden zusätzlich zum Hash im Klartext beim Eigentümer gespeichert, damit der Quizmaster sie erneut anzeigen kann; wer die Tabelle lesen kann, kann sie daher nutzen (Zugriff auf die Tabelle über IAM eng halten). Der Entzug der Gruppe `Quizmasters` wirkt erst nach Ablauf des ID-/Access-Tokens (60 Minuten); für sofortigen Entzug zusätzlich `aws cognito-idp admin-user-global-sign-out` ausführen. Die Betreiberangaben in `src/config/legal.ts` sind in einem öffentlichen Repository dauerhaft sichtbar.

## Architektur und Zugriff

Eine DynamoDB-Tabelle verwendet `pk` und `sk` für Vorlagen, Sitzungsmetadaten, immutable Frage-Snapshots, Identitätszuordnungen, Antworten, Ergebnisse und Timeraufträge. Ein GSI auf 16 Timer-Shards unterstützt die Wiederaufnahme ausstehender Aufträge. Codes werden transaktional reserviert. Gäste können keine Tabellen direkt lesen oder schreiben.

Admin-Queries und -Mutationen verwenden Cognito User Pool und die Gruppe `Quizmasters`. Gast-Queries und -Mutationen verwenden IAM-Credentials des Cognito Identity Pools; auch angemeldete Identity-Pool-Identitäten können dieselben Mitgliedschaftsprüfungen durchlaufen. Die Cognito-Gruppenrolle erhält dafür explizite Rechte auf die benötigten Gastoperationen, aber kein Veröffentlichungsrecht. Alle Teilnehmer-IDs stammen aus der serverseitigen Bindung an die technische Identität. Eine zweite Browseridentität kann erneut teilnehmen; das MVP kann Mehrfachteilnahme nicht zuverlässig verhindern.

Mitspieler-Avatare kommen aus dem lokalen Katalog `src/domain/avatars.json`; die PNG-Dateien liegen unter `public/assets/avatars/`. Der Server weist beim ersten Join einer Gastidentität pro Sitzung ein freies Motiv zu und legt die Reservierung `AVATAR#<avatarId>` gemeinsam mit Teilnahme und Namensreservierung in einer DynamoDB-Transaktion an. Nach Vergabe aller 50 Motive serialisiert die Sitzungs-Version die Auswahl des aktuell am seltensten verwendeten Motivs. Reservierungen sind nummerierte Slots (`AVATAR#<id>`, `AVATAR#<id>#<n>`) und werden ohne globale Versionsbedingung per `attribute_not_exists` vergeben; konkurrierende Beitritte versuchen es mit Backoff und Jitter erneut. Löscht eine Person ihre Teilnahme, wird ihr Avatar-Slot in derselben Transaktion freigegeben; bestehende Teilnehmerzuordnungen werden nicht ersetzt. Reconnects geben die gespeicherte Zuordnung zurück; Lobby, Spieleransicht, Rangliste und Podest verwenden dieselbe lokale Bildkomponente mit neutralem Fallback.

AppSync-Subscriptions werden bei Registrierung durch Lambda auf gültige Mitgliedschaft, Eigentümerschaft oder Präsentationstoken geprüft und serverseitig nach Sitzung gefiltert. Die Sitzungs-Version steigt nur bei Phasenwechseln (Start, Öffnen, Schließen, Auswertung, Auflösung, Zwischenstand, Ende, Abbruch). Beitritte, Löschungen und Antworten ändern nur Zähler. Ein Stream-Consumer fasst je Stream-Batch (bis zu 100 Records, höchstens 1 s Wartezeit) alle Änderungen einer Sitzung zu einem Ereignis zusammen und veröffentlicht Sitzungs-ID, Version sowie Teilnehmer- und Antwortzahl über eine IAM-geschützte Mutation. Beide Identity-Pool-Rollen und die Quizmaster-Gruppenrolle erhalten eine explizite IAM-Verweigerung für diese Mutation. Clients laden bei höherer Version die jeweils autorisierte Projektion (250 ms entprellt); reine Zähleränderungen werden lokal übernommen, eine geänderte Teilnehmerzahl lädt die Teilnehmerliste gedrosselt (1–2 s) nach. Bei Wiederverbindung wird erneut abonniert und ein Snapshot geladen; ältere Versionen werden ignoriert. Verbindungsfehler werden mit begrenztem Backoff erneut versucht.

Lösung, Erklärung und Verteilung liegen im privaten Snapshot und werden erst nach vollständiger Auswertung in eine separate Projektion übernommen. Die Präsentationsadresse enthält einen zufälligen Token; gemeinsam genutzte Datensätze speichern nur dessen Hash. Der Eigentümer benötigt eine private Kopie zum Wiederöffnen. Die Anwendung setzt `Referrer-Policy: no-referrer` und lädt keine externen Tracker, Schriftarten oder Avatar-Dienste.

Alle Betreiberangaben stehen in `src/config/legal.ts`; solange dort Platzhalter (`[… ERGÄNZEN]`) stehen, zeigen die Seiten einen sichtbaren Entwurfshinweis. HSTS ist bewusst auskommentiert, bis die Produktivdomain feststeht. Teilnehmende können ihre Teilnahme im Spiel löschen (`deleteMyParticipation`, nur wenn keine Frage läuft); bereits veröffentlichte, anonyme Antwortverteilungen einer Frage (`REVEAL#…`) werden dabei bewusst nicht nachträglich korrigiert; die gemeinsame Gast-Kennung bleibt für andere offene Runden erhalten. Ihre lokale Gültigkeit endet standardmäßig 24 Stunden nach der ersten Speicherung und wird durch Lesen oder erneutes Schreiben nicht verlängert. Für ein Quiz zum Mitmachen kann sie gezielt bis zur beim Start bekannten Ergebnisaufbewahrungsfrist verlängert werden; ein vorzeitiges Rundenende verkürzt eine bereits verlängerte Frist nicht. Ein offener Tab bereinigt sie bei Fristablauf und bei Rückkehr in den Tab; dabei wird auch der separate, nur im Arbeitsspeicher gehaltene AWS-Credential-Cache verworfen. Wenn der Browser geschlossen ist, erfolgt die physische Bereinigung erst bei der nächsten Ausführung. Das ist keine serverseitige Sicherheitsgrenze und löscht keine serverseitige Spielteilnahme. Cognito ist im Backend auf Access-/ID-Tokens von 60 Minuten und Refresh-Tokens von einem Tag konfiguriert; Refresh verlängert die Refresh-Frist nicht und es gibt keine „Angemeldet bleiben“-Option. Die Werte, Token-Synchronisation über Tabs und Hosting-/CDN-Antwortheader einschließlich `Set-Cookie` sind nach Deployment in der Zielumgebung zu bestätigen. Weitere Betreiber- und AWS-Prüfpunkte stehen in `docs/rechtliche-betreiber-checkliste.md`. Dieses Repository löst keinen automatischen Produktionsdeploy aus.

## Fristen und Auswertung

Eine Transaktion legt Countdown und dauerhaften Timerauftrag gemeinsam an. DynamoDB Streams starten einen Step-Functions-Standard-Workflow; ein minütlicher Sweep nimmt liegengebliebene Aufträge wieder auf. Step Functions rundet Wartezeitpunkte auf Sekunden ab, deshalb werden Öffnung und Deadline für den Wait-Zustand auf die nächste Sekunde aufgerundet. Ein verspäteter Workflow verlängert die Antwortfrist nicht.

`serverReceivedAt` wird beim Eintritt in den AppSync-Lambda-Handler gesetzt. Die Übertragung bis zu diesem Punkt einschließlich Netzwerk und AppSync zählt zur Antwortzeit; exakte Messung am Gerät wird nicht versprochen. Die Transaktion akzeptiert Erstabgaben und Änderungen nur bei `opensAt <= serverReceivedAt < closesAt`, prüft Mitgliedschaft, Antwortoption und offenen Zustand und speichert die Auswahl sowie ihren Zeitpunkt atomar. Der Antwortzähler steigt nur bei der ersten Abgabe pro Person und Frage; die Sitzungs-Version bleibt bei Antworten unverändert. Ältere parallele Anfragen überschreiben keine neuere Änderung; unterschiedliche Auswahlen mit gleichem Serverzeitstempel werden als Konflikt behandelt. Wiederholungen der aktuell gespeicherten Auswahl sind idempotent und verändern weder Zeitpunkt noch Zähler; ihre reine Bestätigung ist auch nach Fristende möglich. Es gibt kein zusätzliches Wechsellimit, das bestehende Schutzlimit von 30 Antwortanfragen je technischer Identität und Minute gilt weiterhin.

Die Auswertung schließt zuerst atomar, liest danach konsistent und schreibt pro Person Ergebnis und Punkte idempotent. Sie berücksichtigt ausschließlich die letzte gespeicherte Auswahl; für `elapsedMs`, Geschwindigkeitspunkte und die Antwortzeit im Ranking zählt der Zeitpunkt der letzten tatsächlichen Änderung. Ohne Wechsel zählt die Erstabgabe. Nach vollständiger Auswertung erscheint die Auflösung; erst nach Freigabe durch den Quizmaster wechselt die Oberfläche zum Zwischenstand. Die bestehende Präsentationsprojektion kann bereits in der Auflösung Top-5-Daten enthalten, diese werden dort nicht mehr zusätzlich unter die Frage gerendert. Korrekte Antworten erhalten `500 + round(500 * (1 - elapsedMs / durationMs))` Punkte, falsche und fehlende Antworten null. Sortiert wird nach Punkten, Anzahl richtiger Antworten und deren gesamter Antwortzeit; identische Werte erhalten denselben Wettbewerbsrang. Die Auswertung schreibt Ergebnisse parallel (höchstens 25 gleichzeitig). Scheitert sie direkt nach dem manuellen Schließen, wird der Fehler protokolliert und Timer bzw. Sweep holen sie nach.

Quiz zum Mitmachen (im eigenen Tempo; intern weiterhin `ASYNC`/`asyncQuiz`): Beim Veröffentlichen vergibt der Server einen 6-stelligen Quiz-Code (Zeichenkette, führende Nullen gültig, Anzeige gruppiert „004 281“). Live-Spielcodes und Quiz-Codes teilen sich denselben Codebereich `CODE#<code>`/`META`: Quizrunden reservieren ihren Code atomar in derselben Transaktion wie Runde, Eigentümerindex, Idempotenzeintrag und Tokenzeiger, und zwar dauerhaft ohne `ttl` (Eintrag `{ publicationId, kind: "ASYNC", createdAt }` ohne Teilnehmerdaten). Ein Code einer Quizrunde wird daher nie neu vergeben – auch nicht nach Ende oder TTL-Löschung der Runde –, damit verteilte QR-Codes, Links und Codes nie auf eine andere Runde zeigen. Live-Codes bleiben nach Ablauf wiederverwendbar; neue Reservierungen übernehmen nur freie oder abgelaufene Live-Codes (`JOIN_CODE_FREE_CONDITION`). Kollisionen werden mit begrenzt vielen neuen Kandidaten (20) beantwortet, danach gibt es eine klare Fehlermeldung (Kapazitätsgrenze: dann `JOIN_CODE_LENGTH` erhöhen). Idempotente Wiederholungen liefern denselben Code.

Teilnahme über den kurzen Link `/q/<Quiz-Code>` (Inhalt von QR-Code und „Link kopieren“), über die gemeinsame Beitrittsseite `/join` („Mitspielen“: ordnet den Code per `resolveJoinCode` eindeutig Live-Quiz oder Quizrunde zu, ohne Versuch oder Beitritt anzulegen) oder über alte lange Links `/q/<Token>`: Token (43 Zeichen) und Code (6 Ziffern) sind disjunkt und lösen auf dieselbe Veröffentlichung auf; Versuch, Wertung und Timer hängen allein an Veröffentlichung und Gastidentität. Runden aus der Zeit vor den Quiz-Codes erhalten beim Öffnen der Verwaltung einmalig serverseitig einen stabilen Code (`ensureAsyncJoinCode`, auch bei parallelen Tabs derselbe Code); ihre alten Links bleiben gültig. Die Verwaltung zeigt kompakte Karten (Status, „Mitspielen bis“, Quiz-Code, kurze Adresse, Teilnehmerzahlen, „Einladung anzeigen“, „Link kopieren“, „Ergebnisse ansehen“; „Vorzeitig beenden“ unter „Weitere Aktionen“). „Einladung anzeigen“ öffnet `/einladung/<Quiz-Code>`: eine screenshotfähige 16:9-Fläche mit Titel, Quiz-Code, Anleitung, QR-Code (Fehlerkorrektur M, Ruhezone 4 Module), Endzeitpunkt und kurzer Adresse, optional im Vollbild. Die Seite enthält keine Admin-Daten, gleicht die Uhr mit dem Server ab und zeigt nach Ende weder QR-Code noch Code.

Neue Async-Quizrunden erlauben 250 Teilnahmen (`ASYNC_MAX_PARTICIPANTS`), unabhängig vom Live-Limit. Bereits laufende Runden mit kleinerem Limit werden nach dem Backend-Deployment beim nächsten Zugriff (auch über die Verwaltungsübersicht) atomar auf 250 angehoben. Beendete oder abgelaufene Runden sowie bereits höhere Limits bleiben unverändert. Der 251. neue Versuch wird abgelehnt; bestehende Teilnahmen können auch bei voller Runde fortgesetzt werden. Spielnamen sind innerhalb einer Runde durch atomare `NAME#<displayName>`-Reservierungen eindeutig, auch bei gleichzeitigen Starts. Bei Kollisionen wird ein neuer Name mit einer zufälligen Zahl versucht; eine Zahl an jedem Namen ist daher nicht nötig. Über verschiedene Runden hinweg können Namen mehrfach vorkommen.

Veröffentlichungen laufen höchstens 90 Tage (serverseitig erzwungen, im UI angezeigt). Die `durationSeconds` der Fragen werden ignoriert; es gibt kein hartes Zeitlimit pro Frage. Neue Veröffentlichungen speichern die Wertungsversion `ASYNC_SPEED_V1`: Eine richtige Antwort bringt 1.000 Grundpunkte plus einen Tempo-Bonus von `round(500 * (1 - elapsedMs / 30000))` (mindestens 0), falsche oder fehlende Antworten 0 Punkte. Bei aktivierten Streak-Boni kommt die oben beschriebene Staffel hinzu. `elapsedMs` misst der Server ab der serverseitig gespeicherten Freigabe der Frage (`currentQuestionStartedAt`, gesetzt erst durch `startAsyncQuiz` – also „Quiz starten“ bzw. „Weiter zu Frage N“) bis zum Eingang der Antwort; Netzwerkwege zählen mit, ein Neuladen setzt den Startzeitpunkt weder zurück noch startet es eine Frage. Grundpunkte, Tempo-Bonus, Streak-Bonus, Gesamtpunkte und Antwortzeit werden pro Antwort gespeichert und gemäß der Veröffentlichungsoption freigegeben. Ältere Veröffentlichungen ohne Wertungsversion bleiben bei einem Punkt pro richtiger Antwort (`LEGACY_CORRECT`). Die Fragenansicht entspricht dem Live-Quiz (Antwortkacheln A–D); ein Tipp gibt die Antwort sofort endgültig ab. Danach folgt eine Pause-Seite mit optionaler persönlicher Auflösung, Fortschritt und „Weiter zu Frage N“, auf der man bis zum Ende der Veröffentlichung unterbrechen und später auf demselben Gerät weiterspielen kann. Bei `ASYNC_SPEED_V1` liefern Antwortbestätigung und `getMyAsyncState` die nächste Frage erst nach „Weiter“, damit sie in der Pause nicht sichtbar ist und der Tempo-Bonus nicht läuft; Antworten auf noch nicht geöffnete Fragen lehnt der Server ab. Ältere Veröffentlichungen (`LEGACY_CORRECT`) liefern die nächste Frage weiterhin direkt mit, die Pause entsteht dort nur in der Oberfläche. Die Aufbewahrung wird beim Beenden einer Veröffentlichung angepasst, nicht in Lesepfaden.

Die Admin-Ergebnisseite zeigt während der Runde den vorläufigen Zwischenstand und danach den Endstand: Die ersten drei Teilnehmenden stehen auf dem Podest in der Anordnung 2–1–3, die weiteren Plätze darunter. Rangfolge: Punkte, dann Spielname, dann eine stabile Versuchs-ID; gleiche Punkte ergeben denselben Rang und dieselbe Podesthöhe. Der sichtbare Stand, die Teilnehmerzahlen und die Fragenauswertung werden etwa alle 10 Sekunden aktualisiert; bei Rückkehr zum Tab oder nach Wiederherstellung der Verbindung erfolgt ein sofortiger Abgleich. Hintergrund-Tabs pausieren die regelmäßigen Abfragen. Bei Fehlern bleiben die letzten Daten mit Warnung und Aktualisierungszeit sichtbar; nach Ablauf der bekannten Aufbewahrungsfrist werden sie auch bei fehlender Verbindung ausgeblendet. Der Zeitstempel bezeichnet den letzten erfolgreichen Abruf, nicht den Zeitpunkt der letzten Antwort.

„Vollbild anzeigen“ präsentiert ausschließlich Titel, Status, Podest, weitere Plätze, Teilnehmerzahlen und Aktualisierungsstand. Reicht der Platz nicht, wechseln die weiteren Plätze automatisch alle 8 Sekunden; der Wechsel kann pausiert werden. Escape oder „Vollbild beenden“ führt zur Adminansicht zurück. Falls der Browser die Fullscreen-API ablehnt oder nicht unterstützt, bleibt eine bildschirmfüllende Fensteransicht mit entsprechendem Hinweis nutzbar. Die Präsentation ist kein öffentlicher Link: Sie erfordert dieselbe Admin-Anmeldung und Eigentümerberechtigung wie die Ergebnisseite. Spielnamen, Avatare und Punkte sind für Personen sichtbar, die auf den Bildschirm sehen; Frage- und Antwortdetails bleiben in der Adminansicht.

`getAsyncStandings` liefert der Adminansicht alle Rangplätze und die aggregierte Fragenauswertung ohne Einzelantworten; bei aktuellen Veröffentlichungen entfallen dadurch die Einzelantwortabfragen bei jedem Abgleich. Ältere Veröffentlichungen ohne Aggregate verwenden weiterhin den Legacy-Antwortscan. Teilnehmerdetails werden erst bei geöffneter Detailansicht seitenweise angefordert und anhand von `attemptId`, Antwortzahl und Punkten mit dem aktuellen Stand abgeglichen; während eines Nachladens oder bei Fehlern werden nicht passende Details als veraltet gekennzeichnet. Die automatische Übersicht erfordert das Deployment des aktualisierten Backends und Frontends.

In der Übersicht unter `/admin` stehen laufende Live-Sitzungen und aktive Quizrunden als Karten oben. Beendete oder abgebrochene Sitzungen sowie vorzeitig beendete oder abgelaufene Quizrunden liegen darunter jeweils in einem standardmäßig eingeklappten Bereich mit Anzahl („Beendete Sitzungen“, „Beendete Quizrunden“). Dort erscheinen sie als kompakte Zeilen mit Status, Datum und Link zur Sitzung bzw. zu den Ergebnissen.

## Hosting und Betrieb

In Amplify Hosting das Repository mit Gen-2-Backend verbinden und den Backend-Build mit den gewünschten Umgebungsvariablen konfigurieren. Die versionierte `amplify.yml` deployt das Backend und kopiert dessen erzeugte `amplify_outputs.json` vor dem Frontend-Build nach `public/amplify_outputs.json`. Das Build-Artefakt ist `dist`; der Build schlägt fehl, falls die Ausgabe fehlt.

Für React Router in Amplify Hosting unter **Rewrites and redirects** eine Rewrite-Regel mit Status **200 (Rewrite)** auf `/index.html` einrichten. Als Quelle eignet sich `</^[^.]+$|\.(?!(css|gif|ico|jpg|js|png|txt|svg|woff|woff2|ttf|map|json)$)([^.]+$)/>`; vorhandene Dateien wie `/amplify_outputs.json` müssen direkt ausgeliefert werden. Nach dem Deployment prüfen, dass `/admin`, ein kurzer Teilnahmelink `/q/<Quiz-Code>` und `/einladung/<Quiz-Code>` (auch nach Neuladen) mit Status 200 die App und `/amplify_outputs.json` JSON mit den Kennungen des passenden Backend-Deployments liefert.

Die Definition benötigt unter anderem CloudFormation-, CDK-Bootstrap-, IAM-, Cognito-, AppSync-, WAFv2-, DynamoDB-, Lambda-, SQS-, EventBridge-, Step-Functions- und CloudWatch-Berechtigungen. IAM-Rollen und Policies werden durch CDK erstellt. Die Tabelle ist mit `RETAIN` definiert, dennoch kann `ampx sandbox delete` Sandbox-Ressourcen einschließlich dieser Tabelle löschen (so auch in der geprüften Sandbox). Vor jeder Löschung Daten sichern und den tatsächlichen Ressourcenstatus prüfen; gegebenenfalls erhaltene Tabellen nach Identitäts- und Inhaltsprüfung separat entfernen.

Sitzungsdaten, Codes, Teilnahmen, Antworten, Ergebnisse und Timeraufträge erhalten DynamoDB-TTL; die Bereinigung erfolgt asynchron. Der Zugriff endet bereits zum gespeicherten Ablaufzeitpunkt, nicht erst beim physischen TTL-Löschen. Quizvorlagen bleiben bis zur aktiven Löschung erhalten; die Übersicht lädt nur Titel, Beschreibung und Fragenanzahl seitenweise (je 100), das vollständige Quiz erst beim Öffnen. Lambdas loggen strukturiert als JSON mit Request-ID und Operation; unbekannte Fehler erreichen Clients nur als generische Meldung. CloudWatch-Alarme überwachen Workflowfehler, Sweep-Fehler und getrennte Dead-Letter-Queues der Stream-Consumer (`FailedTimerEvents`/`TimerDispatchFailures` für Timer-Dispatch, `FailedGameEvents`/`GameEventPublishFailures` für den Event-Publisher); Alarmaktionen/Benachrichtigungsziele sind separat einzurichten. Bei Fehlern Logs und Queue prüfen; der Timer-Sweep prüft nur noch nicht übergebene oder seit mehr als zwei Minuten überfällige Timer und versucht sie erneut und verarbeitet andere Aufträge auch bei einzelnen Fehlern weiter. Er läuft maximal 50 Sekunden pro Minute und ist kein Nachweis für eine beliebig große Zahl gleichzeitig laufender Sitzungen; bei dauerhaftem Rückstau Kapazität, Fehlermeldungen und AWS-Limits prüfen. Nicht zugestellte Echtzeitereignisse nach Wiederherstellung durch erneutes Abonnieren und Laden des Snapshots ausgleichen; es gibt keinen automatischen Replay-Worker für die Publisher-DLQ.

## Integrationsprüfungen

Die folgenden Tests erstellen isolierte Testdaten und benötigen passende AWS-Rechte. Sie können Kosten verursachen. Die DynamoDB-Tests legen eigene Tabellen an und löschen diese nach dem Test:

```sh
AWS_PROFILE=<profil> AWS_REGION=eu-central-1 npm run test:aws
AWS_PROFILE=<profil> AWS_REGION=eu-central-1 QUIZRUSH_LOAD_TEST=1 npx vitest run src/server/load.aws.test.ts
```

Für den browserbasierten Live-Test eine eigens dafür eingerichtete Sandbox-Ausgabe angeben. Die Tests erstellen und löschen temporäre Cognito-Benutzer und legen Spieltestdaten in der Sandbox an; bereits vorhandene `public/amplify_outputs.json` wird absichtlich nicht überschrieben. Der Registrierungstest nutzt die öffentliche Kontoanlage, bestätigt das Testkonto anschließend über `AdminConfirmSignUp` und prüft die manuelle Gruppenfreigabe samt Token-Aktualisierung. Er benötigt entsprechende Test-Adminrechte und prüft **keine echte E-Mail-Zustellung**. Bestätigungscode-Eingabe und Fehlerfälle sind separat mit kontrollierten Browserantworten abgedeckt; der Empfang einer echten Bestätigungs-E-Mail muss mit einem eigenen Testpostfach geprüft werden.

AWS_PROFILE=<profil> AWS_REGION=eu-central-1 QUIZRUSH_LIVE_OUTPUTS=<absoluter-pfad-zu-amplify_outputs.json> \
  npx playwright test e2e/live.spec.ts --workers=1
AWS_PROFILE=<profil> AWS_REGION=eu-central-1 QUIZRUSH_LIVE_OUTPUTS=<absoluter-pfad-zu-amplify_outputs.json> \
  QUIZRUSH_APPSYNC_LOAD_TEST=1 npx vitest run src/server/appsyncLoad.aws.test.ts

Der AppSync-Lasttest prüft in einer Sitzung 100 Gastidentitäten, gleichzeitige Beitritte und Antworten sowie 100 gleichzeitig angemeldete WebSocket-Abonnements, die alle mindestens die letzte Antwortversion empfangen. Er simuliert nicht 100 vollständige Browser mit Snapshot-Abfragen bei jedem Ereignis und hinterlässt Spieltestdaten in der angegebenen Sandbox; diese ist ausschließlich für Tests zu verwenden und danach einschließlich gegebenenfalls erhaltener Testtabellen zu bereinigen. Testergebnisse gelten nur für die konkret geprüfte Konfiguration und sind keine Zusage unbegrenzter Skalierbarkeit.
